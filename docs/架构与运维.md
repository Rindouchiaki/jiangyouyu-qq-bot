# 架构与运维手记

这份是踩坑记录，写给以后的我。环境：Windows 11 IoT LTSC、Ryzen 5 3600X、16 GB、非管理员账号。

## 一、端口与进程

| 组件 | 监听 | 说明 |
|---|---|---|
| SnowLuma WebUI | `127.0.0.1:5099` | 首次启动控制台打印初始密码；改 `webui.json` 前先停进程 |
| OneBot HTTP | `127.0.0.1:3000` | 用 `<ONEBOT_HTTP_TOKEN>` 校验；账号 Load 之后才监听 |
| OneBot WS | `127.0.0.1:3001` | 同上 |
| 反向 WS | `ws://127.0.0.1:18080/onebot/v11/ws` | SnowLuma 作为客户端连 NoneBot，token `<ONEBOT_ACCESS_TOKEN>` |
| 本地视觉模型 | `127.0.0.1:11435` | llama.cpp + Qwen3-VL-2B，`/health` 返回 200 即可用；默认开，`VLM_ENABLED=0` 时一键启动和看护都不拉起它；一键部署按 `external.lock.json` 的 `vision` 下载到 `tools\llama.cpp`、`tools\vl-model` |

端口冲突预案：8080 常被 Steam 的 `steamwebhelper`（remote-debugging-port）占用，所以 NoneBot 一律用 18080 起步。

## 二、SnowLuma 的几个坑

1. **WebUI 初始密码只在「全新数据目录的第一次启动」打印一次**，日志文件里还被脱敏；不先改密就会每次重启重新生成。
   解决办法：`config/webui.json` 删掉，用 `SNOWLUMA_WEBUI_BOOTSTRAP_PASSWORD` 注入种子密码（已有凭据时环境变量不生效）。
2. **账号级 `onebot_<uin>.json` 是 overlay**：两个号配置一样时会抢同一组 3000/3001，后加载的报 `EADDRINUSE`；
   反向 WS 仍然各自正常，所以「另一个号也在回消息」通常不是端口问题，而是没做账号过滤。
3. `statusCommand`（群里发 `#sl` 查状态）默认开着，会把 SnowLuma 名字和版本暴露给任何群友，自用建议关掉。
4. 默认监听是 `127.0.0.1`（源码 `makeDefaultOneBotConfig`），文档写的 `0.0.0.0` 是错的。
5. `engines.node` 实际要求 `^24.22.1 || >=26.12.1`，win-x64 的包自带 node，别用系统的旧 node 起。

## 三、NoneBot 侧

- **账号守卫**：SnowLuma 会把所有已登录账号的事件推到同一个 NoneBot。在 `bot.py` 里用
  `nonebot.message.event_preprocessor` + `IgnoredException` 拦掉 `self_id != BOT_UIN` 的事件
  （`run_preprocessor` 只作用于单个 matcher，挡不住解析插件）。
- **会话键**：NoneBot 默认 `get_session_id()` 是 `group_<gid>_<uid>`，换个群友说「继续」就接不上；
  这里统一压成群级 `group_<gid>` / 私聊 `private_<uid>`。
- **日志编码**：Windows 控制台默认 GBK，loguru 碰到 emoji 会 `UnicodeEncodeError` 把日志打崩。
  启动前必须 `PYTHONIOENCODING=utf-8`，`PYTHONUTF8=1` 更保险。
- **脚本文件编码**：所有 `.ps1` 存成 **UTF-8 with BOM**，否则 PowerShell 5.1 读中文注释会报
  `Unexpected token ')'`。
- **进程保活**：从工具/后台 job 里 `Start-Process` 起的进程会随 job 结束被回收；要长期运行得用
  `Invoke-CimMethod -ClassName Win32_Process -MethodName Create` 分离启动，或用计划任务（非管理员建不了）。
- **OpenCV / ffmpeg**：`nonebot-plugin-parser` 合并音视频需要 ffmpeg，没装时静默「1 项媒体下载失败」；
  用 `imageio-ffmpeg` 里的静态 ffmpeg 并把 `bin` 前置到 PATH 即可。

## 五、排障顺序

1. `scripts/start-all-here.ps1 -Status` 看四个端口是不是都有人听。
2. 18080 有人听但群里没反应 → 看 `logs/nonebot.out.log` 里有没有 `Bot <uin> connected`，以及事件是不是被
   `Event ... is ignored` 吃掉（账号守卫）。
3. 有事件但没回复 → 看 persona 日志：`这次不接（概率闸门）`、`跳过（冷却中 …）`、`冬眠模式，不回话`、
   `会话已翻篇，这句不补了`、`正在冷处理这段时间`、`害羞躲着，不说话`（被追问害羞的事跑开了，10 分钟后自己回来）。
   消息不是立刻回的：先攒几秒再一起回（防抖），这是刻意的。
4. 图片没图卡 → 看 `图片图卡 -> …`；如果一直没有，检查 `IMAGE_CARD_ENABLED` 和图段里有没有 `url`。
5. 视频不下 → 日志里找 `视频时长 xxx 秒, 超过 480 秒, 取消解析`，是插件限额不是网络问题。

## 六、B 站相关的两条链路（解析 vs 推送）

链接解析（有人贴链接）和订阅推送（Bison 轮询）是**两套独立代码**，互不调用，两条都保留：

| | 解析 | 推送 |
|---|---|---|
| 入口 | `nonebot_plugin_parser`（`bot/bot.py` 里 `load_plugin`）+ `bot/plugins/parser_video_only.py` | `nonebot_bison`（`bot/bot.py` 里 `load_plugin`）+ `bot/plugins/bili_push.py` |
| 触发 | 群里/私聊有人贴了链接 | 订阅轮询（动态 60s、开播 60s、番剧 30s） |
| 产出 | 卡片图；视频类只发视频（`parser_video_only.py` 把封面卡片剔掉） | 通知（文字 + 截图）一条 + 合并转发一条；视频/直播只发一条 |
| 怎么关 | `PARSER_DISABLED_PLATFORMS` 里加平台，或干脆不加载插件 | 群里 `/推送 关`；或订阅会话的 `enabled` 置否；或 `bot.py` 不 `load_plugin("nonebot_bison")` |

两边唯一会串的地方：SnowLuma 把机器人自己发的消息也当事件推上来，推送里的链接被解析插件再抓一遍，
就会「推送 → 解析 → 再推送」套娃。现在挡了两道，两条链路各管各的：

1. **自己发的消息直接丢**：`bot/bot.py` 的 `_only_bot_account` 里消息事件 `user_id == self_id` 就
   `IgnoredException`，机器人发的通知、卡片、合并转发都进不了解析。
2. **刚推过的链接不再解析**：`bot/push_marks.py` 记下这次推送里出现过的链接（默认 15 分钟，
   `PUSH_LINK_TTL` 可调，0 不记），`bot/bot.py` 的 `_skip_pushed_links`（`run_preprocessor`）
   只对解析插件查 `contains_recent()`，命中就不解析；人设和别的插件照常收到这条消息（被 @ 照样回）。

推送内部还有两套卡片渲染，都保留着：

- `_shot_card(url)`（主用）：用 htmlrender 共享的浏览器打开 `www.bilibili.com/opus/<动态 id>`，隐藏顶栏后截正文区
  （最多 `BILI_SHOT_MAX_HEIGHT` 像素），
  实测 1.8–2.2 秒；按链接缓存 10 分钟（`_CARD_TTL = 600`），同一条动态订了多个群只截一次。
- `_drawn_card(post)`（兜底）：截图失败或超 35 秒时本地画——头像、昵称、时间、正文、最多 4 张配图、来源。

换推送形态看两个地方：`bot/bot.py` 的 `bison_use_pic_merge`（`2` = 合并转发）决定第二条长什么样；
`bili_push.py` 的 `_send_msgs_with_notice` 决定「通知 + 合并」是发两条还是一条。
